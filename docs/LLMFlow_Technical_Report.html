LLMFlow: An Intelligent LLM Inference Gateway with Semantic Caching and Cost-Aware Routing

A Production ML Engineering Case Study

Varun Reddy Bhimavarapu

Independent Research & Engineering Project

Abstract

Organizations deploying Large Language Model (LLM) applications face escalating operational costs and latency challenges as usage scales. A mid-size application processing 10,000 LLM queries per day on a single cloud provider incurs approximately $1,500 in monthly inference costs. This paper presents LLMFlow, a production-grade intelligent LLM inference gateway that addresses these challenges through three key contributions: (1) a two-tier caching architecture combining exact-match Redis lookups with BERT-based semantic similarity matching, achieving a 67% cache hit rate — an 80% improvement over exact-match-only approaches; (2) a complexity-aware routing engine that classifies queries on a 0–100 scale and routes them to the optimal provider from a pool of three (Ollama, Groq, Gemini), reducing per-query cost by 96%; and (3) a comprehensive observability stack with PostgreSQL query logging, Prometheus metrics, and Grafana dashboards for real-time cost intelligence. In benchmarks, cached queries returned in 6.23ms average (48× faster than uncached), and the system sustained 50+ queries/second under load with a 100% success rate. The combined effect of intelligent routing and semantic caching reduces monthly inference costs from $1,500 to $20 — a 98.7% reduction.

Keywords: LLM inference optimization, semantic caching, sentence embeddings, multi-provider routing, cost optimization, MLOps, production ML systems

Introduction

The proliferation of Large Language Models (LLMs) has created a new category of infrastructure challenge: managing the cost, latency, and reliability of LLM inference at scale. Unlike traditional API services where compute cost per request is negligible, each LLM inference call consumes significant resources — cloud providers charge per token, latency ranges from hundreds of milliseconds to several seconds, and rate limits constrain throughput.

Existing solutions fall into two categories: (a) single-provider SDKs that offer no optimization layer, and (b) proprietary gateway products (e.g., Portkey, Helicone) that provide routing but lack semantic caching or cost-aware intelligence. Neither category adequately addresses the needs of cost-sensitive production deployments.

This paper presents LLMFlow, an open-architecture LLM inference gateway that combines three optimization strategies:

  1. Semantic Caching: Using sentence-BERT embeddings (all-MiniLM-L6-v2, 384 dimensions) to identify semantically equivalent queries and serve cached responses, even when surface-level phrasing differs.
  2. Complexity-Aware Routing: A heuristic classifier that scores queries on a 0–100 complexity scale and routes them to the optimal provider — trading off between cost, speed, and reasoning capability.
  3. Production Observability: Full-stack monitoring with PostgreSQL query logging, 15+ Prometheus metrics, and 11-panel Grafana dashboards for real-time cost and performance intelligence.

The system is fully containerized with Docker Compose and designed for one-command deployment. All components are open and replaceable, allowing organizations to adapt the architecture to their specific provider ecosystem.

2.2 Request Lifecycle

Each incoming query follows a deterministic pipeline with three decision points:

  1. Exact Cache Lookup — An MD5 hash of the normalized prompt is checked against Redis. If found, the cached response is returned in ~1ms with zero LLM cost.
  2. Semantic Cache Lookup — If exact match misses, the prompt is embedded using sentence-BERT and compared against all stored embeddings via cosine similarity. If any stored embedding exceeds the configurable threshold (default: 0.80), the associated response is returned in ~13ms.
  3. LLM Routing — If both caches miss, a complexity classifier scores the query and routes it to the appropriate provider. The response is then stored in both cache tiers for future lookups.

Every request — whether cached or not — is logged to PostgreSQL with full metadata (prompt, response, provider, model, latency, cache behavior, complexity score, and estimated cost). This enables retrospective analytics without impacting the hot path.

Semantic Caching

Traditional caching mechanisms rely on exact string matching, which fails when users express the same intent with different phrasing. In production LLM applications, this is the norm rather than the exception — users rarely type the same query verbatim. Our semantic caching layer addresses this limitation using dense vector representations.

3.1 Embedding Model

We use the all-MiniLM-L6-v2 model from the sentence-transformers library, which produces 384-dimensional dense embeddings optimized for semantic similarity tasks. The model was selected for its balance of quality and inference speed:

3.2 Similarity Computation

For each incoming query, the system generates an embedding vector q and computes cosine similarity against all stored embeddings {e1, e2, ..., en}:

similarity(q, ei) = (q · ei) / (‖q‖ × ‖ei‖)

Equation 1. Cosine similarity between query embedding q and stored embedding ei.

If max(similarity) ≥ threshold (default: 0.80), the corresponding cached response is returned. The threshold was tuned empirically to balance precision (avoiding false matches) with recall (catching valid semantic equivalences).

3.3 Storage Strategy

Embeddings are serialized as JSON arrays and stored in Redis with a configurable TTL (default: 3600 seconds). Each cache entry contains: the original prompt, the embedding vector (384 floats), the LLM response, provider metadata, and a timestamp. The maximum number of stored embeddings is capped at 1,000 entries with LRU eviction.

Complexity-Aware Routing

Not all queries require the same level of model capability. A factual lookup ("What is 2+2?") can be handled by a small local model, while a multi-step reasoning task ("Analyze the trade-offs between consistency and availability in distributed systems") benefits from a larger, more capable model. Our routing engine exploits this asymmetry to minimize cost without sacrificing quality.

4.1 Complexity Classification

The classifier assigns a complexity score between 0 and 100 based on a weighted combination of heuristic features:

  • Query length — Longer prompts tend to be more complex (weight: 0.2)
  • Vocabulary diversity — Unique word ratio indicates conceptual breadth (weight: 0.2)
  • Keyword signals — Presence of terms like "analyze," "compare," "trade-offs," "implement" (weight: 0.3)
  • Structural complexity — Multi-clause sentences, conditional language (weight: 0.15)
  • Domain specificity — Technical terminology density (weight: 0.15)

4.3 Fallback Chains

Each routing decision includes a fallback chain to handle provider failures gracefully. If the primary provider is unavailable or returns an error, the system automatically tries the next provider in the chain:

  • Simple queries: Ollama → Groq → Gemini
  • Medium queries: Groq → Gemini → Ollama
  • Complex queries: Gemini → Groq → Ollama

This ensures zero-downtime operation even when cloud providers experience rate limiting or outages. The fallback mechanism is transparent to the client — the response includes a fallback_used flag for observability.

The dashboard is provisioned automatically via Docker Compose configuration.

7.2 Asynchronous Architecture

The entire request pipeline is fully asynchronous, built on Python's asyncio event loop via FastAPI. Redis operations use aioredis, database writes use asyncpg connection pools (min: 2, max: 10 connections), and Ollama calls use async HTTP clients. This ensures that no single slow operation blocks other concurrent requests.

Related Work

LLM Gateways: Portkey.ai and Helicone provide commercial LLM gateway solutions with request logging and basic routing. However, they lack semantic caching and complexity-aware routing, relying instead on manual provider selection or simple round-robin strategies.

Semantic Caching: GPTCache (Zilliz, 2023) introduced the concept of LLM response caching using embeddings. LLMFlow extends this approach by integrating semantic caching with complexity-aware routing and production observability in a single deployable system.

LLM Routing: Martian's model router and OpenRouter provide multi-model routing based on cost and capability. LLMFlow's contribution is the integration of automatic complexity classification with routing decisions, removing the need for manual model selection.

Sentence Embeddings: The all-MiniLM-L6-v2 model (Reimers & Gurevych, 2019) provides the embedding backbone. Its compact size (22M parameters) and fast inference make it suitable for inline cache lookup without GPU requirements.

Future Work

Several optimization opportunities have been identified for future iterations:

  • ML-Based Complexity Classification: Replace the heuristic classifier with a fine-tuned model trained on labeled query-complexity pairs for improved routing accuracy.
  • Adaptive Threshold Tuning: Implement online learning to dynamically adjust the semantic similarity threshold based on user feedback (e.g., was the cached response satisfactory?).
  • Vector Database Integration: Replace brute-force cosine similarity search with approximate nearest neighbor (ANN) search using a vector database (e.g., Qdrant, Weaviate) for sub-linear scaling beyond 10,000 cached entries.
  • Request Batching: Aggregate multiple queries targeting the same provider and send them as a batch to reduce per-request overhead.
  • Streaming Support: Implement Server-Sent Events (SSE) for streaming LLM responses to reduce perceived latency for long-form generation.
  • A/B Testing Framework: Support routing experiments to compare model quality across providers for equivalent queries.

Conclusion

LLMFlow demonstrates that the real engineering challenge in production AI is not model development, but building the infrastructure that makes LLM inference economically viable at scale. Through the combination of semantic caching and intelligent routing, the system achieves a 98.7% reduction in inference costs while simultaneously improving response latency by 48× for the majority of queries.

The key insight is that most LLM queries in real-world applications are semantically redundant — users ask the same questions in different ways. By exploiting this redundancy with sentence-BERT embeddings, LLMFlow turns a cost liability into a performance advantage. The remaining queries that do reach LLM providers are routed to the most cost-effective option capable of handling their complexity level.

The system is fully containerized, deployable in under five minutes, and provides comprehensive observability through PostgreSQL analytics and Grafana dashboards. Every component is designed for production: async I/O throughout, automatic failover chains, and minimal database overhead (less than 2ms per request).

The complete source code, benchmarks, and documentation are available at github.com/B-VARUN-REDDY/llmflow.
